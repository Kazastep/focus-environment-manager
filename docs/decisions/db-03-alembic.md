# ADR-0002: Миграции базы данных (Alembic)

**Статус:** Принято

**Область:** Database / Backend

**Задача:** DB-03 — Модели и миграции

## 1. Контекст

В рамках DB-01 реализована схема PostgreSQL с четырьмя таблицами на SQLAlchemy Core.

Первоначально таблицы создавались через `MetaData.create_all()`. Этот способ подходит для создания отсутствующих таблиц, но не управляет изменениями существующей схемы.

Для дальнейшей разработки требуется версионирование структуры БД и возможность воспроизводить её на новых окружениях.

## 2. Принятые решения

### Alembic

Для управления миграциями выбран Alembic.

Причины:
- Совместимость с SQLAlchemy Core.
- Автоматическая генерация миграций на основе `MetaData`.
- Версионирование изменений схемы.
- Возможность применения и отката миграций.
- Хранение истории изменений в Git.

### SQLAlchemy Core

Существующая реализация моделей через `Table`, `Column` и `MetaData` сохранена.

Для генерации миграций используется общий объект `metadata_obj` из `database/models.py`.

Переход на ORM для выполнения DB-03 не требуется.

### Асинхронное подключение

Alembic настроен с использованием `asyncpg` и асинхронного шаблона миграций.

Используются:
- `async_engine_from_config`
- `pool.NullPool`
- `AsyncConnection.run_sync()`

Параметры подключения загружаются через `settings` из `database/config.py`.

URL формируется с помощью `URL.create()`, что позволяет корректно обрабатывать специальные символы в учётных данных.

Реальный пароль не хранится в `alembic.ini`.

## 3. Реализация

Настроены следующие файлы:

- `alembic.ini` — конфигурация Alembic.
- `alembic/env.py` — подключение `metadata_obj` и настроек PostgreSQL.
- `alembic/versions/2a34f7dbc70a_initial_schema.py` — первоначальная миграция.
- `database/config.py` — формирование объекта URL подключения.

### Первоначальная миграция

**Ревизия:** `2a34f7dbc70a`

Миграция создаёт четыре таблицы:

- `users`
- `sessions`
- `events`
- `statistics`

Сохраняются первичные и внешние ключи, обязательность полей и ограничения уникальности, определённые в моделях SQLAlchemy.

Функция `upgrade()` создаёт таблицы с учётом зависимостей по внешним ключам.

Функция `downgrade()` удаляет таблицы в обратном порядке.

## 4. Проверка реализации

Для проверки создана отдельная пустая база данных `focus_migrations_test`.

Выполнены:

- Генерация первоначальной миграции через `--autogenerate`.
- Проверка содержимого созданного файла.
- Применение `alembic upgrade head`.
- Проверка текущей ревизии через `alembic current`.
- Проверка созданных таблиц в PostgreSQL.

**Результат:** миграция успешно создала четыре таблицы проекта и служебную таблицу `alembic_version`.

### Существующая база данных

Основная база `focus_db` содержала таблицы до внедрения Alembic.

Первоначальная ревизия зарегистрирована через:

```bash
alembic stamp head
```

Команда не изменяет структуру таблиц, а фиксирует текущую ревизию в `alembic_version`.

Соответствие существующей схемы моделям требует отдельной проверки через `alembic check`.

## 5. Последствия решения

- Дальнейшие изменения структуры БД выполняются через новые миграции Alembic.
- Файлы миграций добавляются в Git вместе с изменениями моделей.
- Перед применением необходимо проверять автоматически сгенерированные операции.
- `MetaData.create_all()` больше не используется как основной механизм создания и обновления схемы.
- Откат миграций проверяется на тестовом окружении из-за возможной потери данных.

## 6. Последующие улучшения

- Проверить соответствие схемы основной БД через `alembic check`.
- Добавить проверку миграций в CI.
- Настроить автоматическое применение миграций при развёртывании.
- Добавить индексы и новые ограничения по мере развития backend и аналитики.

# ADR-0001: Архитектура базы данных

**Статус:** Принято

**Область:** Database / Backend

**Задача:** DB-01 PostgreSQL

## 1. Контекст

Focus Environment Manager собирает информацию о рабочих сессиях пользователя, активности приложений и времени бездействия.

Для MVP требуется постоянное хранение данных, поддержка связей между сущностями и возможность получать историю активности для аналитики.

## 2. Принятые решения

### PostgreSQL

Выбрана реляционная СУБД PostgreSQL.

Причины:

- Поддержка связей PK/FK.
- Ограничения целостности данных.
- SQL-запросы для аналитики.
- Поддержка JSONB.
- Совместимость с SQLAlchemy.

### Docker Compose

PostgreSQL запускается в Docker-контейнере.

Причины:

- Единое окружение для участников команды.
- Быстрый локальный запуск.
- Фиксация версии PostgreSQL.
- Возможность сохранять данные в Docker volume.

### SQLAlchemy Core

Для первоначальной реализации выбран SQLAlchemy Core через `Table`, `Column` и `MetaData`.

Причины:

- Явное описание структуры таблиц.
- Построение SQL-запросов средствами Python.
- Сохранение контроля над SQL.
- Возможность дальнейшего перехода на ORM при необходимости.

### Асинхронная работа с PostgreSQL

Для backend выбран асинхронный подход:

- `create_async_engine`
- `async_sessionmaker`
- `AsyncSession`
- `asyncpg`

Причина — возможность обрабатывать несколько запросов без блокировки цикла событий во время ожидания операций базы данных.

Синхронный `psycopg` также использовался при изучении SQLAlchemy, но не является основным способом доступа к БД.

## 3. Модель данных

### users

Хранит сведения о пользователях:

- `user_id` — PK.
- `user_name` — уникальное имя.
- `user_email` — уникальная почта.
- `password_hash` — хеш пароля.

### sessions

Хранит рабочие сессии:

- `session_id` — PK.
- `user_id` — FK на `users`.
- `started_at` — начало сессии.
- `ended_at` — окончание сессии, может быть NULL.

Связь: один пользователь имеет много сессий (1:N).

### events

Хранит события активности:

- `event_id` — PK.
- `session_id` — FK на `sessions`.
- `timestamp` — время события.
- `app` — приложение.

Связь: одна сессия имеет много событий (1:N).

### statistics

Хранит агрегированную статистику пользователя за день:

- `statistics_id` — PK.
- `user_id` — FK на `users`.
- `statistics_date` — дата статистики.
- `total_focus_time` — суммарное время фокуса.
- `idle_ratio` — доля времени бездействия.
- `top_apps` — наиболее используемые приложения.
- `session_count` — число сессий.

Связь: один пользователь может иметь много записей статистики за разные даты (1:N).

Несколько рабочих сессий могут учитываться в одной дневной статистике. Прямой внешний ключ между `statistics` и `sessions` не требуется: агрегирование выполняется по пользователю и дате.

## 4. Отдельные технические решения

### Уникальность дневной статистики

Для таблицы `statistics` используется составное ограничение уникальности:

```python
UniqueConstraint("user_id", "statistics_date")
```

Это запрещает создавать две записи статистики одного пользователя за одну дату.

### Хранение top_apps

Выбран тип PostgreSQL `JSONB`.

Он позволяет хранить список приложений, а в будущем расширить структуру данными о времени использования каждого приложения.

### Незавершённые сессии

Поле `sessions.ended_at` допускает `NULL`.

Это необходимо, поскольку при создании сессии время её окончания ещё неизвестно.

### Ограничения данных

Используются:

- `primary_key=True` для идентификаторов.
- `ForeignKey` для связей.
- `nullable=False` для обязательных значений.
- `unique=True` для уникальных полей.
- `UniqueConstraint` для составной уникальности.

## 5. Что пока не входит в DB-01

- Реализация CRUD в FastAPI.
- Авторизация пользователей.
- Расчёт аналитики.
- Интеграция Desktop Agent с базой.
- Миграции Alembic.
- Продакшен-развёртывание PostgreSQL.

Эти возможности будут реализованы в последующих задачах.

## 6. Последующие улучшения

- Добавить Alembic для миграций.
- Согласовать окончательные имена полей Pydantic и SQLAlchemy.
- Пересмотреть структуру `top_apps` при реализации аналитики.
- Добавить индексы под реальные запросы истории и событий.
- Перенести операции с базой данных в отдельный слой доступа к данным.
- Удалить или изолировать учебный синхронный код SQLAlchemy.

# Работа с доской проекта

Для управления задачами используем **GitHub Projects**. Все задачи оформляются как GitHub Issues, назначаются исполнителям и отслеживаются на доске проекта.

## 1. Статусы задач

| Статус | Описание |
|---|---|
| Задачи на будущее | Задача существует, но пока не запланирована к выполнению. |
| Готово к работе | Задача понятна, согласована и может быть взята разработчиком. |
| В работе | Разработчик приступил к выполнению задачи. |
| На проверке | Работа выполнена, открыт Pull Request и ожидается Review. |
| Завершено | Pull Request проверен и смержен, задача закрыта. |

**Правила изменения статусов:**

- «В работе» — разработчик устанавливает вручную.
- «На проверке» — автоматически, если настроен соответствующий Workflow; иначе вручную.
- «Завершено» — автоматически при закрытии Issue, если включён соответствующий Workflow.

## 2. Работа с задачами

Каждая задача должна быть небольшой, иметь понятный результат и по возможности выполняться в рамках одного Pull Request.

Полный цикл работы:

```text
Issue создан
      ↓
Задачи на будущее
      ↓
Готово к работе
      ↓
Разработчик берёт задачу
      ↓
В работе
      ↓
Создание отдельной ветки
      ↓
Разработка и коммиты
      ↓
Создание Pull Request
      ↓
На проверке
      ↓
Review и исправления
      ↓
Squash and merge
      ↓
Завершено
```

Перед началом работы разработчик назначает себя исполнителем Issue и переводит задачу в статус «В работе».

Не следует одновременно брать несколько крупных задач. Желательно завершить текущую задачу, прежде чем приступать к следующей.

## 3. Поля задачи

Для планирования используем следующие поля:

| Поле | Назначение |
|---|---|
| Исполнитель (Assignees) | Разработчик, ответственный за выполнение задачи. |
| Статус (Status) | Текущее состояние задачи. |
| Приоритет | Высокий, средний или низкий. |
| Демонстрация | Этап разработки, к которому относится задача. |
| Linked pull requests | Связанные с задачей Pull Requests. |

### Приоритеты

**Высокий** — важная задача, от которой зависит дальнейшая разработка или работа других участников.

**Средний** — необходимая задача, выполнение которой можно запланировать после основных зависимостей.

**Низкий** — дополнительная задача, не блокирующая текущую разработку.

Приоритет не определяет, когда разработчик должен приступить к задаче. Для этого используются статус и поле «Демонстрация».

## 4. Связь Issue и Pull Request

Для каждой задачи создаём отдельную ветку.

Например:

```text
Issue #1
BE-01 Настроить базовый FastAPI backend
```

Название ветки:

```text
feature/1-fastapi-setup
```

В описании Pull Request указываем:

```text
Closes #1
```

GitHub связывает Pull Request с соответствующим Issue.

После открытия PR задача переводится в статус «На проверке» вручную либо настроенным Workflow.

После проверки и слияния PR в основную ветку GitHub автоматически закрывает связанный Issue, если используется поддерживаемая закрывающая ссылка. При включённой автоматизации закрытия задач статус проекта меняется на «Завершено».

**Не закрываем Issue вручную до завершения работы.**

## 5. Представления доски

### Все задачи

Таблица со всеми задачами проекта независимо от их текущего статуса.

Используется для общего контроля работы команды, назначения исполнителей и управления приоритетами.

### Основная доска

Kanban-доска с группировкой задач по статусам.

Позволяет отслеживать текущую работу команды и находить задачи, ожидающие проверки.

### Текущая демонстрация

Отображает задачи, запланированные на ближайшую встречу команды.

Используется для подготовки демонстрации и оценки выполненной работы.

### План разработки

Roadmap для планирования этапов проекта и просмотра задач по времени.

## 6. Планирование демонстраций

Разработка организована небольшими этапами с учётом учебной нагрузки команды.

Перед каждым этапом команда:

1. Проверяет результаты предыдущей демонстрации.
2. Определяет задачи следующего этапа.
3. Назначает исполнителей и приоритеты.
4. Устанавливает поле «Демонстрация».
5. Переводит согласованные задачи в статус «Готово к работе».

Если задача не выполнена к демонстрации, она остаётся открытой и переносится на следующий этап либо возвращается в общий список задач.

## 7. Зависимости между задачами

Некоторые задачи зависят от результатов работы других разработчиков.

Перед началом таких задач необходимо согласовать необходимые интерфейсы, форматы данных и другие технические решения.

Например, Frontend может разрабатываться на тестовых данных до готовности Backend, а проектирование базы данных может выполняться параллельно с созданием FastAPI.

Если выполнение задачи заблокировано, разработчик сообщает об этом команде и указывает причину в комментарии к Issue.

## 8. Структура названий задач

Для всех GitHub Issues используем единый формат:

```text
НАПРАВЛЕНИЕ-НОМЕР Краткое описание задачи
```

### Обозначения направлений

| Префикс | Направление |
|---|---|
| BE | Backend |
| AG | Desktop Agent |
| DB | Database |
| AN | Analytics |
| FE | Frontend |
| INF | Инфраструктура и DevOps |
| DOC | Документация |

### Примеры названий

```text
BE-01 Настроить базовый FastAPI backend
BE-02 Реализовать API рабочих сессий

AG-01 Создать каркас Desktop Agent
AG-02 Реализовать определение активного окна

DB-01 Настроить PostgreSQL
DB-02 Спроектировать схему базы данных

AN-01 Определить метрики активности
AN-02 Реализовать базовую статистику сессии

FE-01 Настроить Frontend-проект
FE-02 Создать макет Dashboard

INF-01 Настроить CI для автоматического тестирования
DOC-01 Обновить документацию API
```

### Правила именования

- Нумерация ведётся отдельно для каждого направления, начиная с `01`.
- Название начинается с глагола: «Создать», «Реализовать», «Настроить», «Добавить», «Исправить».
- Название должно кратко описывать конкретный результат.
- Одна Issue — одна небольшая, проверяемая задача.
- Номер задачи внутри направления не меняется после её создания.

**Важно:** внутренний номер задачи (`BE-01`) и номер GitHub Issue (`#1`) — разные идентификаторы.

Например:

```text
BE-04 Настроить Docker Compose для локальной разработки #16
```

Здесь `BE-04` — внутреннее обозначение задачи, а `#16` — номер, автоматически присвоенный GitHub.

Для названий веток используем номер GitHub Issue:

```text
feature/16-docker-compose
```

Для связи Pull Request с задачей:

```text
Closes #16
```
